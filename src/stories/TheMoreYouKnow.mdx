# The More You Know

Non-obvious things about this codebase that are easy to forget and hard to rediscover. Add to this any time something surprises you.

---

## CSS variable prefix

Every design token is output as a CSS custom property prefixed with `--ds-` (e.g. `--ds-color-action-primary`). The prefix is set in two places:

- **`style-dictionary.config.mjs`** — controls the prefix on the Style Dictionary CSS output
- **`src/system.ts`** — `cssVarsPrefix: "ds"` tells Chakra UI what prefix to use for its internal token lookups

However, changing the prefix also requires a find-and-replace across every recipe file (`Button`, `Card`, `Input`, `Grid`, `Dialog`) and any story files that reference `var(--ds-*)` directly. The strings are hardcoded literals — there is no single source of truth for the prefix beyond the two config files above.

**If you ever rename the prefix:** search the entire `src/` directory for `--ds-` and replace all occurrences alongside the two config file changes.

## Recipe keys must not collide with Chakra built-ins

Chakra UI v3 ships with its own built-in recipes registered under common names like `button`, `input`, and `card`. If you register a custom recipe in `system.ts` under one of those same names, TypeScript will resolve `useRecipe({ key: "button" })` to Chakra's built-in type — not yours — causing variant type errors at compile time even though the runtime behavior is correct.

**The fix used here:** all custom recipes are registered under `ds`-prefixed keys (`dsButton`, `dsCard`, `dsInput`, `dsGrid`) so there is no collision. Keep this convention when adding new recipes.

**Same issue applies to slot recipes:** Chakra owns `"dialog"` as a built-in slot recipe key. Our `Dialog` component works around this by calling its styles object directly from the import rather than going through `useSlotRecipe`.

## Figma variable aliases can silently drift from the token JSON

The DTCG token files (`src/tokens/*.json`) embed `$extensions.figma.variableId` so each token maps to a real Figma variable, but that mapping is a manually-maintained pointer — nothing enforces that the Figma variable's actual alias chain still resolves to the same value the JSON claims.

Found in practice: `component.json` defines `button-bg-disabled` as `{color-neutral-100}`, but the corresponding Figma variable (`button/bg/disabled`) was aliased to `color/surface/subtle` (neutral-50), one shade off from what the code renders.

**If you're building or auditing a Figma component against these tokens:** don't assume the `variableId` in the JSON is sufficient — pull the live variable via `figma_get_variables` and check what it actually resolves to, not just that an ID exists. When re-embedding variable IDs after a Figma-side token edit, diff the resolved value against the JSON's `$value`, not just the reference.

## Storybook does not type-check — CI does

Storybook's dev server and `build-storybook` both use `esbuild` under the hood, which transpiles TypeScript but never type-checks it. TypeScript errors are completely invisible during Storybook development and will pass the Storybook CI job without complaint.

The separate `typecheck` CI job (`npx tsc --noEmit`) is the only gate that catches type errors. If you're seeing something behave unexpectedly and Storybook looks fine, run `npx tsc --noEmit` locally — there may be a type error that esbuild is silently swallowing.

## Chromatic needs no GitHub personal access token

Chromatic authenticates with a **project token** (`chpt_…`) stored as the `CHROMATIC_PROJECT_TOKEN` repository secret. PR status checks come from the Chromatic **GitHub App**, installed via OAuth. A classic personal access token (`ghp_…`) is not part of the flow at any point.

This is worth stating plainly because the sign-in flow makes it look otherwise. If your account belongs to SSO-protected organizations, GitHub interrupts authorization twice, and both prompts invite you to grant org access you don't need:

- **The SAML SSO interstitial** — click **Continue**, not **Authorize**
- **The OAuth consent screen** — leave Organization access at ✗, don't click **Request**

This repo is personal and public, so Chromatic needs zero organization access.

**If Chromatic can't see the repo after declining:** that's the GitHub App installation scope, not the OAuth grant. Settings → Applications → Installed GitHub Apps → Chromatic → Configure, and add the repo there. Creating a personal access token will not fix it — that path was tried and had to be undone.

## Chromatic snapshots your local `build/`, not the repo's

The Chromatic CLI builds Storybook **on your machine** and uploads the static output — it does not clone the repo. Combined with two existing facts, this has a sharp edge: `.storybook/preview.tsx` imports `../build/css/tokens.css`, and `build/` is gitignored.

So whatever token CSS happens to be sitting in `build/` at the moment you run `npx chromatic` is what gets baked into the baselines. Stale output produces baselines that look plausible but encode the wrong values, and every later PR diffs against them. Nothing errors.

**Always run `npm run build:tokens` immediately before a local Chromatic run:**

```bash
npm run build:tokens && npx chromatic --project-token=<token>
```

CI is not exposed to this — the `chromatic` job depends on `build-tokens` and downloads its artifact, so it always snapshots freshly built tokens.

## CI uses `npm install`, not `npm ci` — and must

`npm ci` is normally the right choice for CI: it installs strictly from the lockfile and fails loudly on drift. Here it cannot be used, and the failure is confusing enough to be worth writing down.

Switching the jobs to `npm ci` fails on the Linux runners with:

```
npm error Missing: @emnapi/core@1.11.3 from lock file
npm error Missing: @emnapi/runtime@1.11.3 from lock file
```

`@napi-rs/wasm-runtime` declares `@emnapi/core` and `@emnapi/runtime` as **optional** dependencies at `^1.7.1`. Resolving the tree on macOS skips that branch entirely, so npm writes no top-level entry for either package into `package-lock.json`. On Linux they are needed, `npm ci` refuses to install anything absent from the lockfile, and the job dies before running a single step.

Two things make this hard to diagnose: the error names `@emnapi`, a package nothing in this repo depends on directly, and `npm ci` succeeds locally on macOS — so it only fails in CI.

`npm install --package-lock-only --os=linux --cpu=x64` does **not** fix it. The binding pulling in these deps is `cpu: wasm32`, a fallback target, so resolving for x64 never reaches it.

**Don't convert the jobs to `npm ci`** without first making the lockfile platform-complete, which needs a full regeneration. The workflow carries a comment saying so; this entry is the longer version.
